## Learnings
- 1.3 Pass-1 实际删除 3 行（不是 7 行）：表格中 1 个 Principles 维度行 + 2 个 example 行（PASS / FAIL 各一）。task 文案的 "7 items" 描述指的是 Principles 维度内部 enumerated 的子原则数量（SOLID/DRY/KISS 等），不是文件行数 — 验收以 grep `SOLID|KISS|YAGNI` 全空为准
- E1 audit 的 13-item 切分必须作为不可挑战基线进入 requirements；否则 design 会重做 audit 浪费一轮
- "REVIEW_PASS / REVIEW_FAIL byte-equal" 必须显式列为 NFR-1 + FR-X3，否则 markdown formatter / linter 会无意 normalize 破坏向后兼容
- 双 reviewer 的 verdict 存储 shape（array vs keyed object）是 design 阶段最值得纠结的开放问题，requirements 不预设
- QuickMode bypass 必须在 spec-compliance 侧显式做 reverse 测试（FR-M2），否则实现 bug 会同时降级两边而无人察觉
- 3-layer drift defense 缺任一层都失效 — 必须以 NFR + 测试同时锁定（仅 prose 不够抗 compaction，参考 spec A iron-law 教训）
- D3 keyed-object > array：`reviews.{specCompliance, codeQuality}` 与 spec A `verificationBlocks` 的 keyed-by-phase 同构，O(1) 查找 + 无语义 key 丢失；array-of-{reviewerId,...} 只在未知 reviewer 数量时才赢
- D4 narrowed spec-reviewer 仍跑全 5 phases — code-quality 只在 design/tasks 起作用，不破坏现有 5-file 命令面（minimal disruption 原则）
- D5 复用 state.quickMode 而非新 env var/字段 — 把策略集中到 coordinator 分支，reviewer prompt 保持纯函数（不知道 mode）
- D2 advisory > hard gate：v1 越界 finding 数据点稀疏，hard gate 假阳性代价高；advisory 仍 surface + 让人决定
- File 触点 9 个（4 NEW + 5 EDIT）— 比 plan 暗示的 8 个多 1 个 schemas/spec.schema.json，因 TS 类型变更必须 JSON schema 同步
- 1.4 simple keyword grep 已足够：spec-reviewer.md narrowed 后 `code quality|smell|security|readability|code-quality-reviewer` 全部 0 命中，不需要降级到 section-header regex 方案。如果将来 Pass-2/3/4 引入 cross-reference (e.g. "delegate to code-quality-reviewer")，narrow regex 而不是放宽 forbiddenPatterns 列表
- Task planning: 4 narrowing passes 拆为 Phase 1 (Pass-1 only) + Phase 2 (Pass-2/3/4) — POC scope最小化；spec-reviewer.md 同文件的 Pass-2/3/4 必须串行（2.1→2.2 不能 [P]）
- 2.4 和 2.5 可以 [P]（code-quality-reviewer.md vs references/two-stage-review.md，无文件重叠）；2.7 和 2.8 可以 [P]（design.md vs tasks.md，无文件重叠）
- drift test 既是单元测试又是 e2e（library project，无 dev server）；测试路径 `tests/runner/two-stage-review.test.ts` 对齐现有 buildFreshness.test.ts 同目录
- QuickMode bypass 测试必须显式断言 specCompliance FAIL 仍 block（FR-M2 reverse test）——否则实现 bug 会同时降级两边而无人察觉
- 2.1 Pass-2 narrow shape 同 1.3：1 维度行 + 2 example 行（PASS/FAIL）原地 rewrite，不删行；保留 "Holistic Awareness" 维度 header 和 PASS/FAIL 双列 schema 字节对齐——只压缩 criteria 文字。"5 items" 是维度内部 PASS+FAIL 子句计数（PASS 3 + FAIL 3 ≈ 6，narrow 后各 2 ≈ 4）；以 `grep -c Holistic ≥1` 为成功标志即可（4 hits：维度行 + 2 example 行 + 此前 plan 段落）
- 2.2 Pass-3 (Quality-Gates) 是行内 rewrite（行 117 表格行 + 行 130-131 example 行），保持 PASS/FAIL schema；Pass-4 (Execution/No-Hallucinations) 是整段 cut——Execution Rubric 整个 subsection（描述 + 4 维度行 + 8 example 行）一并搬移到 code-quality-reviewer.md 注释 TODO 块，因为 No Hallucinations 维度无法独立移走（与其他 3 维度共享表格 schema）。task 文案 "6 items" 实际表示整个 Execution rubric 段落体；以 `grep -i hallucination spec-reviewer.md` 0 hits 为成功标志
- 2.4 rubric shape 落在 bullet-per-dimension 而非 markdown 表格——bullets 易于 grep 计数 + 对 Verify 命令 (`grep -c "^- "`) 友好；表格 rows 不以 `- ` 起始会绕过验收。每条 bullet 一个 action verb 起手 (Detect/Reject/Inspect/Verify/Catch/Audit/Demand/Surface/Spot/Flag) — 可读性 + 一致动词 voice 同时拿到
- 2.4 类别落点（共 34 项）：Code smell 6, Security 5, Implementation quality 7, Readability 5, Test quality 5, No-hallucinations 6 — 超出 task 文案 "≥28" 但贴近 "~30" 目标；No-hallucinations 6 项即原 spec-reviewer Pass-4 移出的整段（imports / API calls / file paths / CLI flags / config keys / line refs）
- 2.4 Verify 命令 `grep -c "^- "` 会同时数 When-Invoked / Output Format 等其他 `- ` bullet（基线 22 条），所以只要 Rubrics 段加 ≥6 条就能过 28 阈值——但语义验收 (~30 distinct rubric items) 要求纯 rubric 段单独 ≥28；以 `awk '/^## Rubrics/...{print}' | wc -l` 单独验真而非依赖 Verify 命令。Verify 命令本身是 underspecified 的弱闸门
