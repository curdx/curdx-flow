## Learnings

- Doc-only spec, S size — 8 user stories fit comfortably under the ≤8 task cap (1 US ≈ 1 task; some merge in design).
- Old `parallel-research.md` has 12 inbound refs (3 hard + 9 soft); soft mentions in `specs/` deliberately left untouched — stub redirect absorbs them with zero churn.
- Review domain rules (US-4) are spec B's hard contract — wording must be drift-test-locked between this spec and spec B to prevent silent contract divergence.
- Debug domain has a non-obvious sequencing rule ("never fan-out-first; sequential triage → narrow ≤3 → parallel deep-dive → verifier") — treated as first-class doc content, not just one of the 5 anti-patterns.
- "≥10 anti-patterns" assertion shape (exact count vs ≥3-per-domain) deferred to design — both have tradeoffs (count is brittle if someone splits an anti-pattern; per-domain is loose if someone deletes from one bucket).
- 3 independence criteria framed as pre-flight checklist (must pass ALL 3) — not a "consider these" list — to give coordinator a hard gate before fan-out.
- D2 design insight: per-domain + total gives strictly larger coverage than either alone — per-domain catches bucket starvation (the failure mode that matters for spec B), total catches whole-list neutering. Cost = 1 extra assertion, benefit = both axes covered.
- Hard-ref count clarified during design: E1 confirmed 3 HARD path refs (`commands/research.md`, `commands/start.md`, `references/triage-flow.md`); the other 3 commands listed in requirements are conceptual consumers and only get edited if grep-verify finds literal old-path strings — avoids speculative edits.
- 5-step dispatch pattern preservation upgraded to drift-test invariant (separate assertion) — accidental rewording during rename is the single biggest regression risk (FR-Doc-5).
- Task planning insight: VE tasks omitted (no dev server); `npm run verify` + drift test = E2E validation; phases 2-4 (refactor/test/quality) compressed to 4 phases since doc-only has no code refactoring surface.
