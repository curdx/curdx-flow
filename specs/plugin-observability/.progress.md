## Learnings (design phase)

- **HookStdin 仅 3 字段（cwd/transcript_path/stop_hook_active）**：errors.jsonl 无法直接拿到 sessionId/toolUseID（types.ts:46-50 验证）。AC-1.2 双源 join 退化为 `(hook, ts ±2s, cwd)` 模糊匹配；implement 阶段需评估精度是否够用，不够则需 Claude Code 上游加字段。
- **offset 失效检测降级为 size 倒退**（D-1）：放弃 inode/SHA-256，按 KISS 原则只看 `size < lastSize || mtime < lastMtime` 视为 rotate 全量重读；jsonl 是 append-only 设计，rotate 极少但需在 README 提示。
- **D-3 requestId 缺失 fallback 是隐性兼容性炸弹**：v2.1.119 旧事件无 requestId，与 v2.1.126+ 共存时不能整段丢；fallback 退化为 uuid 单键去重——如果用户混用新旧 session 文件可能漏算 retry，影响 NFR-1 报告精度但保证不挂。
- **redact 走"白名单透出"模式（D-9 配套）**：默认全裁，显式列出可输出字段，新增 schema 字段默认被 redact；implement 时需在 redact.ts 加测试守护，避免 schema map 加 type 时忘改 redact 漏数据。
- **bundle 增量 20KB 是 CI gate 而非软目标**：D-5 lazy import 改造作为 NFR-3 超阈的兜底；implement 时第一版不要预判 lazy，先跑 `wc -c` 实测，超阈才动。
- **--project cwd 推断在非 git 仓库会失败**：R-10 兜底为 exit 0 + warning + 空报告；如果用户在 `~/Desktop` 跑会拿到空报告而非错误，UX 需要清晰的 warning 文案。
- **schema map JSON 与 plugin.json 同分发**（OQ-1 解决）：放 `plugins/curdx-flow/schemas/transcript-events.json`，但 src/analyze/parser.ts 是 npm CLI 的代码，跨包读取需要 `__dirname` 相对路径解析——implement 时确认 tsup bundle 后路径可解（fallback 内置最小白名单已设计为安全网）。

- **POC dedupe was implicit (Map insertion overwrote duplicate uuid lines), filter.ts now explicit (D-2)**: fixture line 9 = exact replay of line 1 (same uuid). ## Learnings (Task 2.3)

- **Verify command's `_shared/run-hook.mjs` path doesn't exist post-bundle** — esbuild's `bundle: true` + `outbase: 'src/hooks'` inlines `_shared/*.ts` into each top-level hook entry. The 4 bundled hooks (`load-spec-context.mjs` / `quick-mode-guard.mjs` / `stop-watcher.mjs` / `update-spec-index.mjs`) each contain a copy of `logHookError`, but no separate `_shared/run-hook.mjs` is emitted. Adapted verify to `grep -l "logHookError" plugins/curdx-flow/hooks/scripts/*.mjs | wc -l` → 4. Spec verify command is correct in spirit, wrong in literal path.
- **Hook name discovery uses `process.argv[1]` basename** — `runHook()` doesn't take a name parameter, so error-logger context derives the name from `path.basename(process.argv[1]).replace(/\.(mjs|js|ts)$/, '')`. Falls back to `'unknown-hook'` for vitest harness / REPL contexts. Trade-off: if a future build flatly renames bundles, hook names in errors.jsonl would shift — accepted because the alternative is threading a name through every `runHook(...)` call site.
- **Cache-busting `--include-prompts`**: idempotent state cache (`lastReportJson`/`lastReportMarkdown`) was a hidden bug — flipping `--include-prompts` would have replayed the previous mode's output. Added `lastIncludePrompts` discriminator to `StateFile` so toggling busts the cache. Same risk class as Task 2.2's "schema map change → cache stale"; Phase 5 should consolidate these into a single cache-version key.
- **`/curdx-flow:research` legitimately survives redaction** — D-9 white-list explicitly preserves extracted command names (`commandHints`). The fixture's `<command-name>/curdx-flow:research</command-name>` markers re-emerge in section 2 (Slash Commands) because that's the report's whole point. The verify hint `grep -q "/curdx-flow:research" /tmp/redacted.md && FAIL` would falsely flag this — refined the verify to `grep -q "command-args"` instead, which targets the actual prompt body that should be hidden.
- **Renderer's `ReportJson` is a minimal projection — `--include-prompts` has no observable effect on report output today**: the renderer never surfaces raw `payload.content` or `payload.message.content` text; it only emits counts, hook names, and command names. So `--include-prompts` is plumbed correctly to `redactEvent` but produces identical reports today. The flag is future-proofing for Phase 4+ when raw stderr / first 200 chars of prompts may be added. ## Learnings (Task 2.2)

- **Idempotent short-circuit MUST be invalidated when shipping a renderer change**: existing `~/.claude/curdx-flow/observability-state.json` cached the OLD POC report (single `## Hook Failures Top-N` section). Without `rm` the new 7-section report would never reach stdout — the cache replays verbatim. - **Schema-map JSON probe order matters for both dev and dist**: from `dist/index.mjs`, `import.meta.url` resolves to `<repo>/dist/`, so the canonical probe is `<repo>/dist/../plugins/...` (one level up). For source runs (e.g. tsx), it resolves to `<repo>/src/analyze/`, so the two-up probe `<repo>/src/analyze/../../plugins/...` covers it. Ship both probes + cwd-relative as belt-and-suspenders. Verified by `mv` → exit 0 + stderr breadcrumb.
- **`tool_use` rows are nested inside `assistant.message.content[*]` in real transcripts** — the schema-map says `tool_use` is its own top-level type, but the fixture (and Claude Code today) embeds them. Rollup walks BOTH shapes (flat + nested) so it works in either world. - **percentile linear-interpolation choice**: `idx = ceil(p * n) - 1` (clamped). For n=1, p=0.5 → idx=0 → returns the only sample. ## Learnings (Task 3.1)

- **vitest 2.x CLI 路径参数 NOT 自动覆盖配置 `include`**：spec hint 说 "用 `npx vitest run` 显式跑 + path 参数绕过 include 限制"，实测 vitest 2.1.9 不工作。`vitest.config.ts` 里 `include: ['tests/hooks/**/*.test.ts']` 是硬过滤，CLI 路径参数得先匹配该 glob 才会被收集。绕过方案：`--config /dev/null` 让 vitest 用默认 include（`**/*.test.ts`）。Task 3.2 应当在 vitest.config.ts 添加 `tests/analyze/**/*.test.ts`，让 spec verify 命令直接生效。
- **snapshot 把 payload 拆掉更稳**：原始 Event.payload 内嵌整个 jsonl 行（含 sessionId 等），写入 snapshot 会让评审看到一墙噪音。改为只保留 `{kind, ts, uuid, requestId?, cwd?}` 5 字段进 snapshot，evidence 仍充分：8 个 event（hook_invocation×4 / assistant_turn×2 / user_turn×2），duplicate uuid `a1111111` 出现 2 次（D-2 dedupe 在 filter 阶段才发生，parser 不去重），第 4 行 `unknown_event_v3` 与第 11 行 `summary` 都正确归到 `unknown_type` 计数器并被 drop。
- **redact grep 测试需谨防 commandHints 误伤**：`includePrompts:false` 默认仍保留 `<command-name>/curdx-flow:research</command-name>` synthesised stub（D-9 白名单透出），所以 `grep -q "/curdx-flow:research"` 永远命中。正确测法：grep 一段**只在原始 prompt 里、不在 hints 里**的字符串（如 `Lorem ipsum` / `command-args` / `plugin-observability` 当 args）。即 Task 2.3 learning 复盘 + 单测落地。
- **filter 的 `--limit` 排序断言要构造 ts 字典序 = 时序**：填充 ms 末三位 `String(i).padStart(3, '0')`，否则 `0:00:00.0Z` < `0:00:00.10Z`（字典序）但 `0:00:00.0Z` > `0:00:00.10Z` 时序上反过来——靠 padStart 拉齐宽度后两序一致。filter.ts:66 的字符串比较隐含此假设（task 2.1 learning 已记，但单测才把它锁死）。

## Learnings (Task 3.2)

- **`vi.mock` + `vi.hoisted` is the only stable way to inject fake fs without polluting other suites**: `error-logger.ts` reads settings.json at module scope (cached). A hoisted `fsState` shared between the mock factory and `beforeEach` lets each test set `settingsContent` / `appendThrow` per case while the mock factory (which runs BEFORE imports) can already see it via closure. Bare `vi.spyOn(fs, ...)` after import is too late — the mocked fs must exist before `error-logger.ts` is imported. Pattern documented for Task 4.x e2e tests if they ever need to inject corrupt state JSON.
- **Top-level `await import` after `vi.mock` is required** so vitest hoists the mock before the module loads. Combined with `__resetCacheForTest()` in `beforeEach`, every case gets a fresh first-read of the mocked settings.json.
- **AC-1.2 fuzzy join distinguishes "same failure recorded twice" from "two failures of the same hook"**: case 3 (ts within ±2s + same cwd) → 1 row, source='merged'. case 4b (same hook but ts > 2s apart) → 1 row but count=2 because `rollupHookFailures` groups buckets by hook name AFTER the ±2s dedupe pass. Initially I wrote case 4b expecting 2 rows but the rollup correctly groups same-hook buckets — adjusted assertion to count=2 with source='merged'. This is the cleaner read of what report.ts:184-194 actually does.
- **`process.stderr.write` spy typing fights with strict ts**: vi.spyOn on stderr.write has overloads that prevent assigning the result to `ReturnType<typeof vi.spyOn>` (param signature mismatch). Used `any` annotation locally with eslint-disable; behaviour fully exercised through `mock.calls` + `mockRestore`. Same issue would hit any future test that spies on stderr.write — preserve this pattern.
- **Snapshot stays small**: I considered also stripping the markdown snapshot to bullet points, but `markdown` is the public output users will inspect — snapshot it verbatim so renderer drift is loud. The fixture deliberately uses 6 events (1 user_turn, 1 agent dispatch, 1 attribution, 2 hook failures, 1 hook success) to keep the snapshot under 50 lines while still exercising all 7 sections.
- **`vitest.config.ts` `include` widened to `tests/**/*.test.ts`** — Task 3.1 learnings flagged the prior `tests/hooks/**` pattern as the reason `npx vitest run tests/analyze/...` needed `--config /dev/null`. With the broadened include, `npm run test:analyze` (`vitest run tests/analyze`) and `npm run test:hooks` (`vitest run tests/hooks`) both honor path filtering naturally. CI gates can compose `test:hooks && test:analyze` per spec verify command.
