# Greenfield Delivery Contract

Use this when `curdx-flow route` reports `topology.workspaceState == "empty"`
or route `greenfield-spec`, `product-inception`, `prototype`, `scaffold`, or
`import-spec`.

## Intent Before Files

Empty workspaces are not automatically small. Route by intent:

| Intent | Action |
| --- | --- |
| `scaffold` | Select the best scaffold source, create only the requested starter/project skeleton, and run baseline verification. |
| `product` with missing facts | Produce product context before application source. |
| `product` with clear facts | Produce greenfield spec, technical plan, walking skeleton, then feature slices. |
| `prototype` | Build the thinnest proof tied to a success criterion. |
| `import-spec` | Normalize the supplied artifact into phase artifacts with traceability. |

## Product Context Artifacts

For product greenfield work, create or reuse:

- `docs/mission.md` -- target user, problem, promise, non-goals.
- `docs/roadmap.md` -- first usable slice, next slices, explicit deferrals.
- `docs/tech-stack.md` -- selected stack, assumptions, commands, external services.
- `docs/constitution.md` -- testing, security, UX, deployment, and verification principles.

Do not duplicate these files if the repo already has equivalent docs. Link or
reference the existing convention instead.

## Walking Skeleton

The first executable greenfield task must prove the system shape works before
business features begin.

For a full-stack app, the walking skeleton should include:

- UI root and package/build scripts
- service root and build/test scripts
- one real health or status endpoint
- one UI route/page that calls the real service
- contract note or OpenAPI placeholder generated by the service when possible
- repeatable verification through `curdx-flow dev detect/up/health/verify/down`

This task is not a throwaway prototype. It is the foundation for later slices.

## Scaffold Source Selection

Scaffold generation is source selection, not framework hardcoding:

- Prefer the official or ecosystem-maintained initializer for the requested
  stack when current docs show one exists.
- Examples are illustrative only: frontend frameworks may expose package-manager
  create commands; JVM services may expose a documented initializer API; other
  stacks may use templates, CLIs, cookiecutters, cargo generators, or no
  generator at all.
- Use self-authored files only when no trustworthy generator exists, the
  generator cannot satisfy the requested constraints, or a smaller custom
  skeleton is easier to verify.
- Record generator choices, versions/commands, assumptions, and deviations in
  `docs/tech-stack.md`, `CLAUDE.md`, or `.curdx/assumptions.md`.
- Never treat one stack's generator as the default for unrelated projects.

## Last-Mile Evidence

Completion requires evidence, not claims:

- project starts from checked-in scripts
- health checks pass
- baseline test/build commands pass
- browser/API integration is verified when UI or full-stack behavior is in scope
- assumptions and deferrals are explicit in the product context or spec artifacts
